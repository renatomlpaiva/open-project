# Plan: Project subtitle

| | |
|---|---|
| **Spec** | ./spec.md |
| **Status** | draft |
| **Created** | 2026-06-14 |

## Approach summary

Add a plain-text, single-line `subtitle` column to `projects` (and the mirrored
`project_journals` table) and surface it through the exact same write pipeline the
existing `name`/`description` attributes already use: model validation +
normalization, `Projects::BaseContract` attribute allow-listing, the
`SetAttributes`/`UpdateService`/`CreateService` `ServiceResult` flow, the API v3
project read + payload representers, and the project general-settings ViewComponent
form. This reuse path is preferred over any new service/endpoint because every
spec requirement (length limit, permission gating, API parity, journaling, copy) is
satisfied "for free" by hooking into the established `Project` attribute machinery.
The 255-char limit mirrors `name`'s `length: { maximum: 255 }` (character count, and
Rails' built-in `:too_long` message is already translatable). FR-11 (trim + strip
newlines, whitespace-only → empty) is handled with a model `normalizes :subtitle`
block, analogous to the existing `normalizes :name, with: ->(n) { n.squish }`.

Rejected alternative: a dedicated subtitle service/contract/endpoint — unnecessary
duplication; the generic project update path already enforces the `edit_project`
permission and is shared by UI and API.

## Data model & migrations

New column `subtitle` (`string`, nullable, no default) on **two** tables:

- `projects.subtitle` — the live column.
- `project_journals.subtitle` — required so `acts_as_journalized` tracks changes
  (the project journal is a column-mirror of `projects`; see the existing
  `project_journals` table which mirrors `name`, `description`, `status_explanation`,
  `workspace_type`, etc.). This satisfies the Decisions note "subtitle changes ARE
  tracked in the project journal."

Migration follows the established pattern in
`db/migrate/20250731144436_add_workspace_type_to_project.rb`: a single migration
using `change_table :projects, bulk: false` and `change_table :project_journals,
bulk: false`. Use `t.string :subtitle, null: true` (nullable for FR-4; no index —
spec excludes filter/sort/search). New timestamped migration class
`ActiveRecord::Migration[8.0]`. `db/structure.sql` will be regenerated by
`db:migrate`. No data migration / backfill (spec explicitly excludes backfill).

Model changes in `app/models/project.rb`:
- `validates :subtitle, length: { maximum: 255 }` (no `presence` — optional).
- `normalizes :subtitle, with: ->(v) { v&.gsub(/[\r\n]+/, " ")&.squish.presence }`
  — strips embedded line breaks, trims, collapses whitespace, and maps
  whitespace-only/blank to `nil` (FR-11, scenario 3 clear-to-empty). `presence`
  ensures cleared values store as `NULL` not `""`.
- Add `"subtitle"` to the existing `register_journal_formatted_fields "identifier",
  "name", formatter_key: :plaintext` line so the journal renders it as plain text
  (distinct from `description`, which uses `:diff`). Journaling of the raw value is
  automatic once the journal column exists; this line only controls display
  formatting.
- (Optional, out-of-scope per spec) do NOT add to `acts_as_searchable` columns.

## Services & contracts

No new services. The generic flow is reused:
- `Projects::SetAttributesService` (`BaseServices::SetAttributes`) assigns writable
  attributes from the contract to the model — no change needed once the contract
  allow-lists `subtitle`.
- `Projects::UpdateService` / `Projects::CreateService` — unchanged; both already
  return `ServiceResult`.

Contract change — `app/contracts/projects/base_contract.rb`:
- Add `attribute :subtitle` (no custom validate block; length/normalization live on
  the model). Placing it on `BaseContract` makes it writable for both Create and
  Update. Authorization is unchanged: `validate_user_allowed_to_manage` +
  `UpdateContract#manage_permission` already enforce `edit_project`, so an
  unauthorized write is rejected via the contract and `subtitle` never reaches the
  model (FR-6, scenario 7). No policy change.

## API (v3)

Reuse existing endpoints (`GET/PATCH /api/v3/projects/:id`, the update form). No new
routes.

- **Read** — `lib/api/v3/projects/project_representer.rb`: add a plain `property
  :subtitle, render_nil: true` (mirror the `name` property — NOT `formattable_property`,
  because subtitle is plain text per FR-3/FR-7/Decisions). Place near the `name`
  property. Cache behaviour follows the representer default (the representer is a
  `CachedRepresenter`; a plain property is included in the cached payload).
- **Write** — `lib/api/v3/projects/project_payload_representer.rb` inherits from
  `ProjectRepresenter`, so once the read property exists and `subtitle` is a contract
  writable attribute, it becomes writable via the payload automatically (FR-8). No
  edit needed in the payload representer unless `writable_attributes` needs the key —
  verify in a request spec; the existing `name` write works the same way, so no
  change is expected.
- **Schema** — `lib/api/v3/projects/schemas/project_schema_representer.rb`: confirm
  whether non-custom attributes are auto-described from the contract's writable
  attributes. If the schema is contract-driven, no change; otherwise add a
  `schema :subtitle, type: "String", required: false`. (Investigate during /tasks;
  low risk either way.)

## Frontend

Project **general settings** page, "Details" section
(`app/components/projects/settings/general/show_component.html.erb`), which renders a
`Primer::Forms::FormList` of `NameForm`, `DescriptionForm`, `Submit`. The controller
+ route + `edit_project` permission already exist
(`config/initializers/permissions.rb` maps `projects/settings/general#update` to
`edit_project`).

- Add a new form object `app/forms/projects/settings/subtitle_form.rb` modeled on
  `name_form.rb`: an `ApplicationForm` with a single
  `f.text_field name: :subtitle, label: attribute_name(:subtitle)` (single-line text
  input — NOT a rich-text area, FR-3). Optional `caption`/help text via i18n.
- Insert `Projects::Settings::SubtitleForm.new(f)` into the `FormList` in
  `show_component.html.erb`, between `NameForm` and `DescriptionForm`, so it saves
  through the same `project_settings_general_path` submit (scenarios 1–4). The
  existing Submit button persists it via `UpdateService`.
- Plain-text rendering is automatic (Primer text_field escapes output → HTML/script
  stored & displayed safely, edge case "HTML/script in value").
- i18n: label via `activerecord.attributes.project.subtitle`; validation message via
  Rails' built-in `errors.messages.too_long` (already translated). No hard-coded
  strings (FR-10).

## Permissions

No new permission. Reuse `edit_project` (Decisions). Enforcement is already wired:
- UI: `projects/settings/general#update` is gated by `edit_project` in
  `config/initializers/permissions.rb`.
- API/contract: `Projects::BaseContract#validate_user_allowed_to_manage` +
  `Projects::UpdateContract#manage_permission` (`:edit_project`).
No `app/policies` change.

## Journal handling

`acts_as_journalized` snapshots all data columns of `projects` into
`project_journals`; adding the `subtitle` column to both tables (migration) is what
makes the value tracked. The `register_journal_formatted_fields ... :plaintext`
addition only governs how the change is *rendered* in the activity/history view.
Decisions require subtitle changes to be journaled "consistent with the description"
— note we deliberately use `:plaintext` (not `:diff`) because subtitle is single-line
plain text. Verify against
`spec/models/projects/project_acts_as_journalized_spec.rb`.

## Test strategy

- **Model** — `spec/models/project_spec.rb`: length 255 accepted / 256 rejected
  (FR-2, edge cases); multibyte counted as characters (255 multibyte chars accepted);
  normalization: leading/trailing whitespace trimmed, embedded `\n`/`\r` stripped to
  single line, whitespace-only → `nil` (FR-11, scenario 3); optional/blank valid
  (FR-4).
- **Journal** — `spec/models/projects/project_acts_as_journalized_spec.rb`: changing
  subtitle creates a journal entry capturing old→new (Decisions: tracked in journal).
- **Contract** — `spec/contracts/projects/update_contract_spec.rb` (+ create): with
  `edit_project`, `subtitle` is in writable attributes; without it, write rejected /
  attribute not writable (FR-5, FR-6, scenario 7). May use
  `spec/contracts/projects/shared_contract_examples.rb`.
- **Request (API v3)** —
  `spec/requests/api/v3/projects/show_resource_spec.rb`: response body includes
  `subtitle` as plain string (FR-7, scenario 5).
  A PATCH/update request spec (e.g. alongside
  `spec/requests/api/v3/projects/update_form_resource_spec.rb` or a new
  `update_resource_spec.rb`): authorized user can write subtitle and read it back
  (FR-8, scenario 6); >255 → 422 with translated message; unauthorized → 403/422 and
  value unchanged (FR-6/FR-8).
- **Component / view** —
  `spec/components/projects/settings/general/show_component_spec.rb` and/or
  `spec/views/projects/settings/general/show.html.erb_spec.rb`: the subtitle text
  field renders with a translated label and is not a rich-text editor (FR-3, FR-10).
- **Feature (Capybara/Cuprite)** — extend the settings-general flow (page object at
  `spec/support/pages/projects/settings/general.rb`): authorized user sets, edits,
  and clears the subtitle and it persists across reload (scenarios 1–4; acceptance
  criterion 1). Mark with the existing JS/feature tags used by sibling settings
  specs.
- **Copy** — `spec/services/projects/copy_service_spec.rb` (or copy specs under
  `spec/services/projects/copy/`): copying a project with a subtitle carries the
  value to the copy. (No code change — `subtitle` is not in `CopyService#skipped_attributes`,
  so `source.attributes.except(*skipped_attributes)` copies it automatically; this
  spec guards the Decisions "subtitle IS copied" requirement.)

Acceptance-criteria coverage: AC1→model+feature; AC2→model+request; AC3→model+component;
AC4→contract+request; AC5→request(show); AC6→request(update); AC7→component/view.

## Risks & rollout

- **Two-table migration**: forgetting `project_journals.subtitle` would silently drop
  journaling and can raise on journal creation. Mirror the workspace_type migration
  precisely.
- **Schema representer**: uncertain whether the v3 project schema auto-derives
  `subtitle`; small follow-up may be needed (low risk).
- **Payload writability**: confirm a plain `property` on the inherited payload
  representer is enough for PATCH writes (it is for `name`); covered by the update
  request spec.
- **structure.sql churn**: `db:migrate` regenerates `db/structure.sql`; commit the
  regenerated file, do not hand-edit.
- **Editions**: no Enterprise/BIM-specific code; community-safe. No feature flag
  needed. Backwards compatible (nullable column, optional field). Copy/templates
  covered automatically.
- **i18n**: run `bundle exec i18n-tasks normalize` / `missing` after adding the key.
